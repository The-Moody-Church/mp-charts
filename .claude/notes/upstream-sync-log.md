# Upstream Sync Log

This fork tracks `MinistryPlatform-Community/MPNext`. Upstream changes are reviewed periodically and cherry-picked selectively — we do **not** merge upstream directly, since the fork has intentionally diverged (e.g., Next.js 16 — upstream recently upgraded to 16 as well).

## How to Check for Upstream Changes

```bash
git fetch upstream
git log main..upstream/main --oneline
```

Or review PRs at: https://github.com/MinistryPlatform-Community/MPNext/pulls

## Review: 2026-09-15

Reviewed upstream PRs #79–#91 (all merged upstream 2026-09-12/13 since the 2026-09-01 review). This is the **Better Auth security hardening**: ten findings, nine fixed upstream, plus a 940-line `docs/security/downstream-hardening-playbook.md` written specifically for forks, and a published advisory — **GHSA-pqxp-c5mr-5398** (High, CVSS 8.1) for the `/update-user` session-identity flaw.

Unlike the last three reviews, **the fork did not lead upstream here.** Two of the highest-severity findings were live in our tree, one of them Critical and inherited verbatim.

**Key strategic decision: everything in this review is applied on the better-auth 1.6 line.** Upstream fixed these on 1.7.4, but every mechanism they used exists in 1.6 — verified against our installed `node_modules`: `disabledPaths` (`dist/api/index.mjs:164`), `account.accountLinking.enabled` (`dist/oauth2/link-account.mjs:23`), `onAPIError.errorURL` (`@better-auth/core` `init-options.d.mts:1343`), `required: true` enforcement (`dist/db/schema.mjs:103`). `release-1.6` is still maintained (1.6.33, 2026-09-14). **The #68 migration remains deferred and is NOT a prerequisite for any security fix here.** Route names and OAuth error codes differ between 1.6 and 1.7, so upstream's allowlist and error-page copy were translated, not copied.

### Things worth carrying forward

- **Our fork is the reference implementation for two siblings.** `mp-senior-care` and `music-db` were copied from this repo and inherit the same auth. Both are being fixed in parallel; `music-db` additionally had `^1.6.11`, which admits 1.7.x, with an open Dependabot PR that would have removed its only sign-in path.
- **`music-db` is the reason to keep the 1.6 evidence written down**: it is *not* vulnerable to F-UPDATE-USER, because its 1.6.11 predates `parseAdditionalUserInputFromProviderProfile` and its fields are still `input: false`. Bumping it without flipping them breaks login; flipping them without `disabledPaths` opens the Critical finding. The two must move in one commit.
- **PKCE (F8) is still open upstream.** We have concrete evidence they do not: `music-db` enabled it on 2026-04-18 (`d80f22e`) and reverted it two days later (`b0d0436`) because MP returned `invalid_grant` at token exchange. Worth sending upstream, and worth a dev-only re-test since MP's IdP has moved on since.
