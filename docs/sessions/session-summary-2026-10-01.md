## Stable Server Actions encryption key — COMPLETED on branch (branch `chore/server-actions-encryption-key`, PR [#247](https://github.com/The-Moody-Church/mp-charts/pull/247))

**Problem.** Next.js derives every Server Action ID from `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` at build time. mp-charts never set it, so each Docker build generated a random key and renamed every action. A tab opened before a deploy then failed its next action with "Failed to find Server Action" until reloaded, and sign-out (`handleSignOut`) is one of those actions. event-manager and mp-senior-care fixed this long ago. music-tools has the same symptom and is being done separately.

**Change (ported from event-manager / mp-senior-care):**
- `Dockerfile`: the builder's `npm run build` step mounts an **optional** BuildKit secret `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` and exports it only if the file exists. The step is identical to the siblings'; the comment is expanded.
- `.github/workflows/docker-build-push.yml`: `secrets:` is added to the `build-scan-and-push` image build only. `verify`, which also runs for Dependabot, keeps no secrets, and comments now say why.
- `.env.example`: the siblings' comment block, plus a line saying both values must match and local dev leaves it blank. *(Superseded by the reconcile below: the key is a build-time secret only.)*
- `DOCKER.md` § Server Actions encryption key (what it fixes, where to set it, how to generate it, what happens without it or when it changes, the cache caveat, a check that prints only match/mismatch, exposure; the runtime half and the match check were replaced in the reconcile below); a GitHub-secrets table row; a pointer under Environment Variables. `README.md`: the env block and production checklist. `CLAUDE.md`: a Next.js 16 note.

**Measured (Next 16.3.8, 89 actions):**
- Two clean `next build`s without a key shared **0 of 89** action IDs. A blank value behaved the same: 0 of 89, and the build succeeded.
- Two with the same test key shared **89 of 89**; a third key changed them all.
- A standalone server from a rebuild with the same key **recognised** the previous build's sign-out ID. The ID from a keyless build got `404` + `x-nextjs-action-not-found: 1` and a logged "Failed to find Server Action". Starting that server with a *different* runtime key did not affect ID lookup.
- Next writes the key verbatim into `.next/server/server-reference-manifest.json` (and the standalone copy), so the image carries it.
- Docker (local daemon, native arm64): the build succeeds with and without `--secret`. With the secret, the image carries that key and gives the same IDs as a local build with it. The test key does not appear in `docker history` or the image `ENV`.
- **Found: BuildKit's cache ignores the secret.** A `--secret` build over a context already built without one came out `CACHED` and shipped the old, keyless key. A second build with a different key did the same. Only `--no-cache-filter builder` picked the new key up.
- `docker/build-push-action@v7` (actions-toolkit `parseSecretKvp`) turns an unset repo secret (`NAME=`) into a warning, "… is not a valid secret", and skips it. The build is unaffected.

- **Verified in Next 16.3.8's own source** (`node_modules/next`) that the runtime env is not needed:
  - Build: `dist/build/index.js:654-658` calls `generateEncryptionKeyBase64({ isBuild: true })`, which returns `process.env.NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` if set, otherwise a random AES-GCM-256 key (`dist/server/app-render/encryption-utils-server.js:92-112`, the env check at `:96-99`). `dist/build/turbopack-build/impl.js:65,111,210` hands it to Turbopack (the action-ID hash salt; `next build` is Turbopack here) and to `TurbopackManifestLoader`, which writes it into `server-reference-manifest.json` (`dist/shared/lib/turbopack/manifest-loader.js:114,134`). The webpack path does the same (`dist/build/webpack-config.js:426,452,1964` `serverReferenceHashSalt`; `flight-client-entry-plugin.js:720`).
  - Runtime action lookup never touches the key: `serverActionsManifest[runtime][actionId]` (`dist/server/app-render/action-handler.js:828`; `manifests-singleton.js:259`). The manifest, key included, is loaded at `manifests-singleton.js:275`.
  - The only runtime reader of the env var is `getActionEncryptionKey` (`dist/server/app-render/encryption-utils.js:78`: `process.env.NEXT_SERVER_ACTIONS_ENCRYPTION_KEY || serverActionsManifest.encryptionKey`). Its callers are `encodeActionBoundArg` / `decodeActionBoundArg` (`dist/server/app-render/encryption.js:45,71`), behind `encryptActionBoundArgs` / `decryptActionBoundArgs` (`:92`, `:189`) and `use-cache-wrapper.js:1471` (only when `boundArgsLength > 0`). That is closure encryption for inline Server Actions and closure-capturing `"use cache"` functions. This app has neither: all 16 `"use server"` directives are file-level, and all six `"use cache"` functions are module-level, with no bound args. Even with closures, an unset runtime env falls back to the manifest copy, which is the stable build key. A runtime copy could only add a second value that might drift.
  - The other callers of `generateEncryptionKeyBase64` are `next dev` only (`dist/server/lib/router-utils/setup-dev-bundler.js:182`, `dist/server/dev/hot-reloader-turbopack.js:315`).
